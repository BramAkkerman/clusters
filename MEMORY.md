# Project memory

This repo is a Flux GitOps mono-repo managing multiple clusters. Layout convention:

- `clusters/<name>/` — Flux bootstrap (`flux-system/`) + top-level `apps.yaml` / `infrastructure.yaml` Kustomizations for that cluster
- `apps/<name>/` — actual app manifests (namespace, HelmRelease, HelmRepository, CNPG Cluster, etc.)
- `infrastructure/<name>/` — supporting infra (cert-manager, cnpg-operator, traefik config, etc.), one subdirectory per component

Both clusters sync from `https://github.com/BramAkkerman/clusters` (this repo), `main` branch, each with its own `path:` into `clusters/<name>`.

**Exception**: apps hosted on self-hosted Gitea live in a *second* mono-repo, `https://git.meneerak.nl/flux/apps` (private, under the `flux` org — not personal `bram/`), separate from this GitHub repo — a deliberate choice (discussed explicitly): mono-repo-per-host, not one-repo-per-app. `dawarich` was the first app moved there as a test of migrating off GitHub; more apps should go there too as `apps/<name>/` inside *that* repo (same convention as this repo), not as additional separate repos. Only Gitea itself (`apps/gitea/` in *this* repo) stays on GitHub — it's the thing hosting the other repo, so it can't depend on it. A thin pointer stays in *this* repo for the Gitea-hosted repo as a whole (one `GitRepository`, `clusters/emk/gitea-apps-source.yaml`, shared by every app hosted there) plus one `Kustomization` per app (e.g. `dawarich`) with `path: ./apps/<name>` and `sourceRef` pointing at that shared `GitRepository` instead of `flux-system` — adding a new gitea-hosted app means a new `Kustomization` block in `clusters/emk/apps.yaml`, not a new `GitRepository`/secret/deploy key. Flux auth to Gitea: SSH deploy key on the `flux/apps` repo (not a personal account credential at all — same principle as how `flux bootstrap` set up the GitHub repo originally). Write access enabled on the same key so it's used for both Flux's pulls and manual pushes. Stored in a `gitea-apps-auth` secret in `flux-system` with the `identity`/`identity.pub`/`known_hosts` keys Flux's SSH auth expects. `GitRepository.spec.url` uses `ssh://git@git.meneerak.nl/...`, not `https://`.
  - **Gitea SSH had to be exposed externally first** — `gitea-ssh` was `ClusterIP`-only, never reachable from outside the cluster (only HTTP(S) ingress was ever set up for Gitea). Rather than provision a second LoadBalancer (right after hitting Cyso's volume quota, didn't want to risk an LB quota too), added a new Traefik entrypoint (`ports.gitssh`, container port `2222` → exposed port `22`) on the *same* LoadBalancer Service, plus an `IngressRouteTCP` (`apps/gitea/ingressroute-ssh.yaml`, `HostSNI(`*`)` catch-all rule — SSH has no SNI to match on) routing it to `gitea-ssh:22`. Confirmed with `ssh-keyscan git.meneerak.nl` before trusting it in a `known_hosts`.

## Clusters

### `zitadel-vm` (kubeconfig context: `zitadel-vm`)
Single-node k3s VM, public IP `81.24.6.55`. Hosts Zitadel at `auth.meneerak.nl`.

- Postgres via CNPG (`apps/zitadel/postgresql-cluster.yaml`), not the chart's bundled Bitnami postgres.
- TLS terminates at k3s's **bundled** Traefik (`kube-system/traefik`, not Flux-managed as a HelmRelease — only its `HelmChartConfig` override is, under `infrastructure/zitadel/traefik-config/`).
- cert-manager + `letsencrypt-prod` ClusterIssuer, HTTP-01 via Traefik.

### `ak` / EMK (kubeconfig context: `ak-oidc` (use this one), plus legacy `ak`, `ak-wildcard`, `ak-internal`)
Cyso Cloud "Enterprise Managed Kubernetes" — Gardener-based (Shoot terminology, `core.gardener.cloud` API), backed by Fuga Cloud's OpenStack. Project `xc3wlbs`, shoot `ak`. Hosts Gitea at `git.meneerak.nl`, was freshly bootstrapped (nothing pre-installed) — Traefik, cert-manager, cnpg-operator are all Flux-managed HelmReleases here (`infrastructure/emk/`), unlike zitadel-vm.

- **Access: use context `ak-oidc`** (authinfo `oidc-zitadel-ak`) — OIDC login against the project's own Zitadel instance, superseding the old dashboard-kubeconfig dance below. Confirmed it silently re-authenticates on an expired/missing token with no manual login step needed (no browser prompt observed even after the token had gone stale) — genuinely no-manual-renewal access, resolving the earlier "possible future" follow-up.
  - Legacy path, kept for reference only: dashboard kubeconfigs (context `ak`) expire in ≤24h; the longer-lived fallback was a 90-day service-account kubeconfig used to mint fresh 24h `adminkubeconfig`s on demand via `kubectl create --raw .../adminkubeconfig`. Shouldn't be needed anymore now that `ak-oidc` works, but the `ak` context is still present in kubeconfig if `ak-oidc` ever has issues.
- Gitea admin user: `bram`, credentials in `gitea-admin` secret (namespace `gitea`, manually created, not in git).
- Gitea DB: CNPG, bootstrap-only (no superuser dance needed — unlike Zitadel, Gitea only needs its own DB user).
- Gitea chart: bundled Bitnami postgres/valkey-cluster subcharts explicitly disabled (default ships a 3-node Valkey cluster — overkill for personal use); using Gitea's built-in in-memory cache/session instead.
- Also hosts Dawarich (self-hosted location history / Google Timeline alternative) at `timeline.meneerak.nl`, migrated off `zitadel-vm` (was running there outside Kubernetes — Docker Compose, not managed by this repo at all). Chart: `Cogitri/charts` dawarich (`https://charts.cogitri.dev`) — community-maintained, explicitly bring-your-own-Postgres (no bundled Postgres dependency at all, unlike Gitea/Zitadel's charts which bundle one you have to disable). It does bundle a `redis-ha` subchart (aliased as `redis:` in values) defaulting to 3 replicas — same overkill pattern as Gitea's Valkey, knocked down to 1 via `redis.replicas: 1`.
  - **PostGIS gotcha**: Dawarich requires the `postgis` Postgres extension. The chart's bundled-Postgres path auto-creates it via an init container, but that path is entirely skipped when bringing your own DB (which we always do) — CNPG's default Postgres image doesn't have PostGIS at all. Fixed with a dedicated image (`ghcr.io/cloudnative-pg/postgis`, pinned by digest, matching the `17.x` major version used elsewhere) plus `bootstrap.initdb.postInitTemplateSQL: [CREATE EXTENSION IF NOT EXISTS postgis;]` on the CNPG `Cluster` — runs against the template DB so it's present before the app database is even created from it.
  - `env.applicationProtocol: "https"` set explicitly up front (chart defaults to `"http"`) — learned from the Zitadel/Gitea TLS mismatches earlier in this project not to leave that implicit behind a TLS-terminating ingress.
  - **Data migrated from the old Docker Compose deployment on `zitadel-vm`** (`docker compose exec dawarich_db pg_dump -U postgres -Fc -d dawarich_development`, then `pg_restore --no-owner --clean --if-exists` into the CNPG `dawarich` database — real numbers: 115k points, 6k tracks, 3.7k visits, all migrated cleanly, geometry columns verified queryable post-restore). Two things worth knowing if this comes up again: (1) `pg_restore` over the CNPG pod's local socket hits **peer auth**, not password auth — connect via `-h 127.0.0.1` to force TCP/password auth instead. (2) The source dump included `postgis_topology` (bundled by the `postgis/postgis` Docker image by default) which our target never created and the `dawarich` app role can't create itself (permission denied) — `pg_restore` reported 8 ignored errors, all topology-extension setup, none touching actual app tables. Dawarich doesn't use topology features for core tracking (points/tracks/trips/visits), so this was left alone rather than chasing it — would need `postInitTemplateSQL` + a full cluster recreate to add properly, same one-shot-at-bootstrap constraint as everything else CNPG's `postInitTemplateSQL` touches.
  - **Zitadel as OIDC IdP**: `oidc.autoRegister` semantics are the *opposite* of what the docs/AI-summarized source implied. Read the actual `app/controllers/users/omniauth_callbacks_controller.rb` (not a summary of it — got this wrong once first) to confirm: with `autoRegister: false`, the app ONLY checks for an already-linked identity (`provider`+`uid` match) and returns `nil` otherwise — it never attempts an email match at all, so "an existing account with a matching email" does nothing on its own. The email-match-with-verification-challenge flow (`Auth::FindOrCreateOauthUser::LinkVerificationSent`, which safely links to an existing account via a confirmation step rather than blindly trusting the email claim) is gated behind `autoRegister: true`. So: `autoRegister: true` is correct and safe here even with a pre-existing account to link to — it doesn't mean "blindly create duplicates," it means "attempt the (verified) email-match/create flow at all." Redirect URI must be exactly `https://<host>/users/auth/openid_connect/callback` (fixed, not derived from the display `providerName`) — confirmed via Dawarich's own docs, not guessed.
  - **redis-ha gotchas from reducing 3 replicas → 1**: (1) `replicas`/`persistentVolume.enabled` live on the STATEFULSET's immutable spec — changing them on an existing release fails the Helm upgrade outright (`Forbidden: updates ... are forbidden`); had to manually `kubectl delete statefulset`+pvc once to let Helm recreate clean. (2) `min-replicas-to-write` defaults to `1` (assumes real HA) — with zero replicas connected this makes the single node refuse ALL writes (`NOREPLICAS`); needs `redis.redis.config.min-replicas-to-write: 0` — note the **double** `redis:` nesting (our chart's alias for the subchart, then the subchart's *own* internal `redis:` key, which is separate from its `sentinel:` key and is where `config:` actually lives). Setting it at `redis.config...` (one level too shallow) is a silently-ignored unknown key — the `HelmRelease` spec looks correct, the rendered ConfigMap doesn't change at all, and the default of `1` stays in effect. Cost a long detour assuming a live pod just hadn't picked up the change, when the real problem was the value never reaching the template in the first place. (3) Random passwords containing `+` broke `redis://:pass@host` URL parsing specifically (confirmed: `redis-cli -a` with the exact same password worked, `redis-cli -u "redis://:pass@..."` failed `WRONGPASS`) even though the plain AUTH command accepted it fine — regenerate with `openssl rand -hex` instead of `-base64` for anything that ends up embedded in a connection URL string, not just used as a raw credential.
  - Deleting an app/sidekiq pod does NOT re-resolve `secretKeyRef` env vars on container *restart* within the same pod (CrashLoopBackOff keeps reusing the env captured at pod creation) — after rotating a secret, `kubectl delete pod` (not just wait for the crash loop) to force fresh env resolution.
  - Hit Cyso's account-level OpenStack **10-volume quota** here — Dawarich alone wanted 5 PVCs (postgres, redis, `public`, `storage`, `watched`). Cut to 3 by disabling redis persistence and the `watched` staging dir (`persistence.watched.enabled: false`, falls back to `emptyDir`). Also: Helm doesn't delete PVCs left orphaned by a values change that removes their reference (e.g. disabling `persistence.watched`) — had to `kubectl delete pvc` the orphan manually to actually free the quota slot.
- Also hosts **wg-easy** (WireGuard VPN, web UI at `wg.meneerak.nl`, tunnel on UDP `51820`) in `apps/wireguard/` — raw Kubernetes manifests, not a Helm chart. Deliberately skipped the community `hansehe/wg-easy-helm` chart: its `secret.create` toggle doesn't actually avoid plaintext — `environmentVariables` renders straight into either a `Secret`'s `stringData` *or* literal env vars depending on that flag, but the source values themselves (in git, in our values) are plaintext either way. Writing it by hand kept `INIT_PASSWORD` on a real `secretKeyRef`, consistent with everything else in this repo.
  - Current wg-easy (v15+) env vars are a full rewrite from older wg-easy versions — no `WG_HOST`/`WG_PORT` anymore, it's `INIT_HOST`/`INIT_PORT`/etc., and per their own docs these `INIT_*` vars are **one-time-only** (read on first boot, ignored after — same "only applies at bootstrap" shape as CNPG's `postInitTemplateSQL` and Zitadel's `FirstInstance`, a pattern that keeps recurring in this project).
  - `INIT_ALLOWED_IPS: "0.0.0.0/0,::/0"` (full-tunnel) was the one config decision that mattered: since cluster-internal IPs are just a subset of "everything," full-tunnel mode satisfies both "personal exit-node VPN" and "reach cluster-internal services" at once, with no separate split-tunnel config needed — connected clients route through the pod's own network namespace, which can already reach both.
  - Requires `privileged: true` + `NET_ADMIN`/`SYS_MODULE` capabilities. Client CIDR `10.8.0.0/24` chosen to avoid EMK's actual pod CIDR (`100.96.0.0/24`-ish, confirmed via `kubectl get nodes -o jsonpath='{.spec.podCIDR}'` before picking a range, not assumed).
  - **`net.ipv4.ip_forward`/`net.ipv4.conf.all.src_valid_mark` via pod-spec `securityContext.sysctls` is `SysctlForbidden` on EMK** — these are "unsafe" sysctls requiring the kubelet to explicitly allow-list them (`--allowed-unsafe-sysctls`), which a managed cluster we don't control the node config for doesn't have set. Real cost of this: **Deployments have no backoff limit the way Jobs do** — every rejected pod gets immediately replaced by a new one, forever, until something scales it to 0. Caught this around ~1300 failed pod objects. Fixed with a **privileged init container** running `sysctl -w` directly instead (shares the pod's network namespace with the main container, so it still takes effect) — works without needing any kubelet-level allow-listing at all. Lesson beyond this specific case: when deploying anything that might hit a cluster-level policy rejection (unknown/managed cluster, first time trying a given security-context feature), scale to `replicas: 0` or watch the rollout actively rather than firing-and-forgetting a `Deployment` — a `Job`'s `backoffLimit` would have stopped this on its own, a `Deployment` will not.
  - UDP port exposed via a new `IngressRouteUDP` + a new named Traefik entrypoint (`wireguard`, port `51820`) — reusing the *same* LoadBalancer IP as everything else, same reasoning as Gitea's SSH exposure (avoid a second LoadBalancer / risk hitting a quota on those too).

## Non-obvious gotchas hit along the way

- **CNPG disables the `postgres` superuser by default** (`enableSuperuserAccess: false`) — no password login exists at all. Zitadel's init job needs that superuser to bootstrap. Fix: `enableSuperuserAccess: true` + explicit `superuserSecret.name`. Once, the CNPG operator didn't pick up this spec change on its own — needed a manual annotation bump to force reconciliation. Gitea didn't need any of this (only needs its own app-user DB access).
- **Zitadel v2.67.2 defaults `TLS.Enabled: true`** internally and crashes without a cert/key if so — must explicitly set `configmapConfig.TLS.Enabled: false` when TLS terminates at the ingress (Traefik).
- **Traefik's HTTP→HTTPS redirect is not automatic**, and the values key differs by chart-version generation. `ports.web.redirectTo.port: websecure` **silently no-ops** on the k3s-bundled chart (helm-install job succeeds, deployment never actually changes) — the real key on the pinned chart versions here is `ports.web.http.redirections.entryPoint.{to,scheme,permanent}`. Without this, Zitadel's own OIDC console client (registered with an `https://` redirect_uri via `ExternalSecure: true`) rejects logins reached over plain `http://` with `redirect_uri is http and is not allowed`.
- **Always verify Helm values against the actual pinned chart version's real `values.yaml`**, not whatever's on the chart repo's `main`/default branch — got burned twice by schema drift between versions (traefik redirect key above, and Zitadel `main`-branch chart docs showing features like `FirstInstance.Org.Machine` that don't exist in the pinned `8.13.4`).
- **`flux bootstrap` only auto-commits its own generated `flux-system/*` files** — hand-authored Kustomizations/manifests (`apps.yaml`, `infrastructure.yaml`, app manifests) still need a manual `git add/commit/push`. Nearly shipped the whole EMK/Gitea setup without ever pushing it — Flux only had the bootstrap files and nothing else reconciled until the missing commit was pushed. Always `git status` before assuming something's live.
- **`flux bootstrap github` needs a GitHub token with deploy-key management permission** — fine-grained tokens need `Administration: Read and write` (not just `Contents`), classic tokens need full `repo`. A 403 on `GET .../repos/.../keys` mid-bootstrap means the token scope, not the bootstrap logic, is the problem; rerunning after fixing the token is safe (idempotent).
- **The cluster autoscaler only reacts to unschedulable (`Pending`) pods — never to actual runtime memory/CPU pressure.** Every app in this project was deployed without `resources.requests`, so the scheduler had no idea how much memory anything actually needed and happily packed pods onto nodes with no constraint — pods only started competing for real memory at *runtime*, which the autoscaler can't see at all. Consequence, hit for real while deploying Immich + a Jellyfin/Radarr/Sonarr/Prowlarr/qBittorrent stack in one session: both original nodes hit 96%/88% memory, and it cascaded into **unrelated, pre-existing services** — Gitea's own CNPG Postgres went `0/1 NotReady` and flapped for ~45 minutes, which broke `claude-bot`'s Gitea API token auth (Gitea's API can't function without its DB), and Flux's own `source-controller`/`notification-controller` started failing health checks too, stalling *all* GitOps reconciliation cluster-wide, not just the new apps. Fix: add real `resources.requests` (based on observed `kubectl top pods --containers` usage, with headroom) to the new apps' heaviest containers. The moment the scheduler saw requests that didn't fit, `cluster-autoscaler` correctly fired (`TriggeredScaleUp`, visible only via pod `describe` events — the autoscaler itself isn't a pod visible from inside the shoot, it runs on Gardener's seed/control-plane side) and grew the pool from 2 nodes to 4 (the account's actual configured max) within a couple of minutes, and everything recovered on its own once headroom existed. **Lesson: every new app from here on needs at least a memory request on its heavier containers** — Dawarich, Gitea, Zitadel, wg-easy, homepage, and freegamesbot still don't have any set, meaning the autoscaler still can't react if any of *them* grow. Retrofitting those is a reasonable follow-up, not yet done.
- **`resources.requests` without a matching `resources.limits` doesn't protect anything from a genuine leak/unbounded-growth bug.** A day after the autoscaler fix above, Immich's rclone sidecar (FUSE-mounting the 4TB `fotos` bucket) grew past 1.5Gi against its 1Gi *request* — no *limit* was set, so nothing stopped it. The node ran low on memory and kubelet **evicted the whole pod** (not an OOMKill — a different, node-pressure-triggered mechanism), and since the Deployment wanted 1 replica it immediately recreated one, which hit the same growth and got evicted again — repeating, unthrottled, for ~26 hours (Deployments have no backoff limit — same root cause as the wg-easy `SysctlForbidden` storm), accumulating ~220 dead pods and taking the whole app offline ("no available server"). Short version: always pair a memory `request` with a memory `limit` on anything FUSE/cache-related, since a limit is what actually contains a leak (clean per-container OOMKill+backoff) rather than just informing the scheduler/autoscaler. (Immich itself, and its `apps/immich/README.md` with the fuller incident writeup, was removed from the cluster on 2026-08-17 - this lesson stays generally applicable to any future FUSE/cache sidecar.)
- **Dawarich's floating `2.x` chart version silently drifted onto an app version that no longer matched our database schema, and the community chart's hardcoded startup-probe timeout nearly turned the fix into another restart storm.** `/trips` started 500ing with `PG::UndefinedColumn: column "latitude" does not exist`. Root cause: the HelmRelease pins `chart.spec.version: "2.x"` (a floating range) which had resolved to chart `2.6.0` → app `1.7.11` — but our actual `points` table has been PostGIS-`lonlat`-only (no `latitude`/`longitude` columns at all) since the very first data migration from the old VM in this project, and `1.7.11`'s `TripsController#set_coordinates` still hand-wrote raw SQL against the old columns. Schema was effectively *ahead* of the app code, backwards from the usual "forgot to migrate" failure mode. Fix: backed up the DB (`pg_dump`, verified restorable before proceeding), overrode `image.tag: "1.11.0"` directly (the `charts.cogitri.dev` community chart repo we use doesn't publish anything newer than app `1.7.11`/`1.8.1`, so this bypasses the chart's own tested chart↔app pairing — accepted as a reasonable risk here since the chart is a thin wrapper around a single container). Confirmed fixed by directly re-running the previously-failing query via `rails runner` and getting real coordinates back, not just "the pod is Running."
  - **Gotcha discovered mid-upgrade**: the chart hardcodes `startupProbe.failureThreshold: 10`/`periodSeconds: 10`/`initialDelaySeconds: 30` (~130s total budget) in an internal `_helpers.tpl` template — not exposed through `values.yaml` at all. A version jump spanning ~30 releases meant `rails db:migrate` + `db:seed` took several minutes on our ~115k-row `points` table, so kubelet kept killing the pod via the startup probe before it ever finished, restarting it from scratch each time (though migrations themselves are idempotent, so each retry picked up further than the last). Fixed by `kubectl patch`-ing the live Deployment's probe `failureThreshold` up to `60` to buy enough time for the one-time slow migration. **Flux reverted that patch on its very next reconcile** (correct drift-correction behavior, not a bug) — but by then the actual migration work was already done and idempotent, so the resulting fresh rollout started fast and succeeded on the tightened default probe anyway. If this chart needs another big version jump in the future, expect the same probe-timeout problem and either pre-empt it with the same temporary patch trick, or reach for a Flux `HelmRelease` `postRenderers` patch for something durable that Flux won't fight (not done here — one-time problem, temporary patch was enough).
- **Gitea's stuck rollout after adding resource limits had two unrelated causes layered on top of each other, and hibernating/waking the cluster only fixed one of them.** After giving Gitea's Postgres and app pod real resource requests/limits (see the autoscaler entry above - this was the retrofit), the new pod got stuck in two different ways in sequence:
  1. First it failed to even reach postgres (`dial tcp ...: connect: operation not permitted`), which looked like a Cilium/networking problem — and it was: the node it landed on (`z2`) had Cilium's own health endpoint timing out under sustained cluster-wide memory pressure from an unrelated Immich incident happening at the same time. This symptom fully disappeared after hibernating and waking the cluster (fresh nodes, fresh Cilium agent state) - didn't require any Gitea-specific fix.
  2. Once past that, a *second*, unrelated issue appeared: `unable to lock level db at /data/queues/common: resource temporarily unavailable`. Gitea's chart defaults `strategy.type` to Kubernetes' standard `RollingUpdate`, which briefly runs the old and new pod at once - fine for stateless apps, broken here because both pods mount the *same* ReadWriteOnce volume and Gitea's internal notification queue is a local LevelDB file lock: the new pod can't acquire it while the old one still holds it. Fixed by setting `strategy.type: Recreate` in the chart's values (same fix already applied to every other single-instance RWO-volume app in this project - Immich, Dawarich, wg-easy, media-stack - Gitea was just the one case where the chart's default hadn't been overridden yet).
  3. Even after switching to `Recreate`, one more restart was needed: a *stale* LOCK file was left over on disk from one of the day's several ungraceful terminations (OOM kills, force-deletes, the hibernation cycle itself). Cleared it by scaling Gitea to 0 and running a throwaway debug pod that mounts the same `gitea-shared-storage` PVC to `rm` `/data/queues/common/LOCK` directly - safe specifically because nothing was holding a live lock on it at the time (Gitea was scaled to zero).
  **Lesson: when a rollout is stuck, check for more than one cause before assuming the first error you find is the only one** — this took three sequential fixes (wait for infra to stabilize, fix the deployment strategy, clear a stale lock file), not one.
- **Flux's drift-correction reverts unpushed live `kubectl apply` changes on its normal reconcile interval, not just "eventually" — for `apps`/`immich`/`media`/`homepage`/etc. that's every 10 minutes.** While setting up Filestash + moving Immich to a new domain, several live fixes (Immich's Ingress host, homepage's ConfigMap) were applied directly to unblock testing before the corresponding commits were pushed. Both got silently reverted by Flux within ~10-20 minutes — caught only because a follow-up `curl` test started failing again after having worked minutes earlier (Immich's old Ingress reappeared and started competing with Filestash's for the same hostname, briefly routing unauthenticated traffic to the wrong app). **Lesson: if a live fix genuinely can't wait for a push (actively testing, mid-debugging), expect Flux to fight it on whatever that Kustomization's `interval` is — verify nothing quietly flipped back before declaring something fixed, and treat "commit but don't push yet" as inherently temporary/fragile for anything Flux manages, not just a formatting preference.**
- **A brand-new app directory under `flux-apps/apps/` does nothing on its own — it needs a matching `Kustomization` added to `clusters/emk/apps.yaml`** (in *this* repo, not `flux-apps`) before Flux will manage it at all. Filestash's manifests sat fully deployed-by-hand for a while with zero GitOps management (no drift protection, but also no risk of Flux reverting it) until this was added. Every existing app (`media`, `immich`, `homepage`, etc.) has one of these; a new app without one is invisible to `flux get kustomizations`.
- **Filestash's `APPLICATION_URL` env var must be a bare hostname, never a full URL — Filestash unconditionally prepends its own scheme on top of whatever you give it.** Set it to `https://fotos.meneerak.nl` (the obvious thing to try) and got `http://https://fotos.meneerak.nl` in every post-login redirect. Root cause, confirmed directly in `server/common/config.go`: `Origin = ("https://" if general.force_ssl else "http://") + general.host`, with no defensive scheme-stripping on `general.host` (which is exactly what `APPLICATION_URL` sets). Fix: bare hostname only, and separately set `general.force_ssl: true` — which has **no env var at all** (admin-console-only field), so it was patched directly into `/app/data/state/config/config.json` on the PVC via `kubectl exec`. That file survives pod restarts (it's on the PVC) but **not a PVC wipe** — worth remembering if Filestash's storage ever gets recreated from scratch. Full writeup in `flux/apps`' `apps/filestash/README.md`.
- **Don't assume sharing a Zitadel app/oauth2-proxy cookie secret across unrelated app groups is a welcome "bonus," even when it enables convenient SSO.** Filestash's oauth2-proxy was first wired to reuse `apps/media`'s exact Zitadel app and cookie secret (same technique, one fewer app to register, and a login on either group would cover both) — explicitly rejected: "I don't want filestash to fall under the same app as the *arr apps." Redone with its own dedicated Zitadel app and a freshly generated cookie secret. **Lesson: technical convenience/elegance (fewer moving parts, bonus cross-app SSO) isn't the same as what's wanted — app-identity boundaries between unrelated services are a real preference here, not just an implementation detail to optimize away.**
- **The original `zitadel-admin` bootstrap password was lost.** Zitadel's setup job prints the auto-generated first-admin password to its own pod logs exactly once, at first-ever setup — and that job re-ran (and its pod got recycled) multiple times during earlier debugging (postgres-auth fix, TLS fix), so the credential is gone. `DefaultInstance.*` config (SMTP, initial admin password) only applies at first-ever instance creation and can't retroactively configure an already-bootstrapped instance. **Resolved**: wiped the CNPG database and let Flux redeploy fresh with `DefaultInstance.SMTPConfiguration` (and a known admin password) baked in from the start — confirmed working end-to-end (e.g. Jellyseerr's email notifications route through this same `zitadel-smtp` secret successfully).

## DNS (`meneerak.nl`)

Migrating DNS delegation from Strato (registrar, `rzone.de` nameservers) to Cyso Cloud DNS (same place the EMK/zitadel-vm servers live). DNSSEC was active during the migration — correct/safe unsigning order is: remove the `DS` record at the registry (`.nl`/SIDN) first, then let the child zone's own signing (`DNSKEY`/`RRSIG` at Strato) wind down after — verify via `dig +short DS meneerak.nl` returning empty, not by trusting Strato's dashboard status flag alone (it lagged behind the actual registry state).

Records in play: `auth.meneerak.nl` → zitadel-vm Traefik (`81.24.6.55`), `git.meneerak.nl` → EMK Traefik LB (`81.24.6.106`, service name `traefik-traefik` — Helm fullname template concatenates release+chart name since both are literally `traefik`).

SMTP for Zitadel: Cyso Cloud's Transactional Email Service ("pidge"), `send.pidge.cyso.cloud:587`, sender `noreply@meneerak.nl`, auth password in the `zitadel-smtp` secret (namespace `zitadel`, on `zitadel-vm`). SPF/DKIM records added at Cyso Cloud DNS.

## Resolved: `DefaultInstance.Org.Human.Password` doesn't actually work — use `FirstInstance`

Set the bootstrap admin's password via `DefaultInstance.Org.Human.Password` (env var `ZITADEL_DEFAULTINSTANCE_ORG_HUMAN_PASSWORD`) and every login attempt failed with "Password is invalid" — confirmed via `claude-in-chrome` driving the actual login form with the byte-verified password directly (ruling out any copy/paste error), and via the eventstore showing real `user.human.password.check.failed` events. The password gets embedded in the `user.human.added` creation event fine, but this specific path is a known, confirmed-by-a-maintainer Zitadel Helm chart bug (see [zitadel/zitadel-charts#156](https://github.com/zitadel/zitadel-charts/issues/156) — "I think you need to use `FirstInstance` instead").

`FirstInstance` is a dedicated section (`cmd/setup/steps.yaml` in zitadel core) specifically designed to reliably override `DefaultInstance` for the first-ever setup — same nesting (`FirstInstance.Org.Human.Password`, env `ZITADEL_FIRSTINSTANCE_ORG_HUMAN_PASSWORD`), and it's the one that's actually reliable. Note `DefaultInstance.SMTPConfiguration` (a *different* subsection) worked correctly the whole time — this bug is specific to `Org.Human` user creation, not `DefaultInstance` as a whole. There's no `FirstInstance.SMTPConfiguration` equivalent, so SMTP config correctly stays under `DefaultInstance`.

## Another gotcha: EMK's Traefik `IngressClass` is `traefik-traefik`, not `traefik`

On EMK, the Traefik HelmRelease is named `traefik` and the chart is *also* named `traefik` — Helm's fullname template concatenates release+chart name when they're literally identical, so every object it creates is `traefik-traefik` (Service, Deployment, and critically the `IngressClass`). Any Ingress (or cert-manager `ClusterIssuer` HTTP-01 solver config) that sets `ingressClassName: traefik` silently matches nothing — Traefik never registers a router for it at all, and requests fall through to Traefik's own generic `404 page not found` (indistinguishable at a glance from a real app-level 404). This cost a long detour debugging a "broken ACME challenge" that was actually just this. Fixed in both `apps/gitea/gitea-release.yaml` (`ingress.className`) and `infrastructure/emk/cert-manager-config/cluster-issuer.yaml` (`solvers[].http01.ingress.ingressClassName`) → `traefik-traefik`. `zitadel-vm`'s k3s-bundled Traefik doesn't have this problem — its `IngressClass` is genuinely named `traefik`, since it's k3s's own add-on, not a same-named Flux HelmRelease. Always check `kubectl get ingressclass` on EMK rather than assuming the name matches the release.
